# Casebook 개발일지 쓰기

하루 동안 한 작업을 개발 블로그의 `개발일지` 글 하나로 정리합니다. 이 저장소의 `README.md` "개발 블로그 글" 규칙을 먼저 읽고 따릅니다. 이 스킬과 README가 다르면 README를 따릅니다.

## 1. 재료 모으기

| 재료 | 어디서 |
|---|---|
| 그날의 커밋 | 글쓴이가 작업한 저장소의 `git log --since=<날짜> --until=<다음 날>` |
| 왜 그렇게 했는지 | 작업한 세션의 대화, 이슈, 결정 기록 |
| 결과 | 배포 · 시험 · 심사 결과 등 실제로 확인된 것만 |

- 확인되지 않은 일은 "예정"이나 "남은 과제"로 씁니다. 끝났다고 쓰지 않습니다.
- 다른 사람의 작업은 그 사람 글에 맡깁니다. 같은 날 여러 사람이 쓰면 파일 이름 뒤에 `-2`, `-3`을 붙입니다.

## 2. 파일과 머리말

`src/content/blog/devlog-YYYY-MM-DD.md` (이미 있으면 `devlog-YYYY-MM-DD-2.md`)

```yaml
---
title: "동사로 끝나는 작업형 제목"
date: YYYY-MM-DD
category: 개발일지
summary: 그날 한 일을 한 문장으로 정리합니다.
author: <글쓴이의 GitHub 닉네임. 운영자는 x-0o0>
---
```

- `cover`는 쓰지 않습니다. 개발일지는 모두 같은 커버가 자동으로 들어가고, 다른 그림을 적으면 빌드가 실패합니다.

## 3. 글 구조

1. `## 개요`: 그날 한 일을 2~3문장으로 씁니다.
2. 작업마다 `## <동사형 소제목>` 하나씩 씁니다. 순서는 문제 → 방법과 이유 → 결과입니다.
3. `## 결과와 남은 과제`: `| 항목 | 상태 |` 표로 마무리합니다.

**톤**
- 합니다체로 쓰고, 소설 같은 제목이나 비유("사건 수첩:", "항해 일지:")는 쓰지 않습니다.
- 3분 안에 읽히게 씁니다. 작업이 많으면 중요한 3~5개만 고릅니다.
- 비교나 목록은 표로 씁니다. 꼭 알아야 할 것은 `> **중요:**`, 덧붙이는 것은 `> **참고:**` 상자에 씁니다.
- 코드는 짧은 예시 코드로 씁니다. 실제 앱 코드를 옮기지 않습니다.
- 그림이 필요하면 2~3가지 색(`#1D1D1F`, `#F5F5F7`, `#D2D2D7`)만 쓴 단순한 그림을 넣습니다. 시스템 사이의 흐름만 그리고 내부 구조는 그리지 않습니다.

## 4. 쓰지 않는 것

| 쓰지 않는 것 | 대신 |
|---|---|
| 이메일, 사용자 · 계정 식별자, 실명 | 쓰지 않거나 "운영자", "팀원" |
| 서버 테이블 · 함수 이름, SQL | "서버", "사건 보관소" 같은 일반 이름 |
| Slack 채널 이름, 저장소 이름, 비밀 값 이름 | "운영 채널", "배포 명령" |
| 커밋 번호 | 쓰지 않음 |
| 보호 장치가 **어떻게** 동작하는지 (권한 범위, 우회 경로, 중복 차단 방식, 대체 경로) | 결과만 씁니다. 예: "같은 명령이 여러 번 들어와도 한 번만 실행되게 막았습니다" |
| 공개 전 사건의 정답, 사용자가 보낸 편지 내용 | 쓰지 않음 |

## 5. 올리기 전 스스로 점검하기

- [ ] 제목이 동사형이고, 소설 같은 표현이 없다
- [ ] 개요 → 작업별 소제목 → 결과와 남은 과제 순서다
- [ ] 4장의 "쓰지 않는 것"을 처음부터 끝까지 다시 찾아봤다 (특히 보호 장치의 동작 방식)
- [ ] 확인되지 않은 일을 끝났다고 쓰지 않았다
- [ ] `cover`를 비웠고 `author`를 적었다
- [ ] `npm run build`가 경고 없이 성공한다

## 6. 승인받고 공개하기

1. 초안을 글쓴이에게 보여 주고 고칠 곳을 받습니다. **승인 전에는 커밋하지 않습니다.**
   - 운영자 쪽 세션은 PM 세션을 거쳐 운영자의 승인을 받습니다.
   - 팀원은 운영자에게 따로 승인을 받은 뒤에 올립니다.
2. 승인을 받으면 `git pull` → `npm run build` → 커밋 → 푸시 직전에 다시 `git pull` → 푸시 순서로 올립니다. 다른 사람의 커밋을 덮어쓰지 않고, force push는 하지 않습니다.
3. 배포가 끝나면 `https://x-0o0.github.io/casebook-legal/blog/<파일 이름>.html`이 열리는지, 블로그 목록에 보이는지 확인하고 결과를 알립니다.
